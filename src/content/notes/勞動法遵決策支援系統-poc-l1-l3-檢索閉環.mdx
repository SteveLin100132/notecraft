前兩篇卡在同一個地方：**法條對不到四大類與主題**。現在那張表來了：《檢核機制_工程師初檢表_A段_L1-L3+L6》，四大類、22 個 L2 主題、85 個 L3 題型，每一列都掛好了對應的勞基法條文。

缺口補上之後，PoC 的核心反而**縮小**了：分類這件事被反查掉，不必再讓模型去猜。

長出來的是外圍的兩塊：一個讓檢索結果**看得見**的 UI，以及一段替尚未交付的 L4~L8 規格暫時頂著的報告 prompt。

## PoC 範圍

**只先做 L1~L3，加上一段暫代的風險分析報告。**

分類這段照舊是反查出來的，不需要模型。變數在後半段：**L4~L8 的規格顧問師還沒交**，必要事實追問、地雷判定、:tip[介入程度]{content="L8 的產出：這一題需要顧問親自介入到什麼程度"}的判定邏輯目前都還是空的。等規格是一種選擇，但那會讓這一版 PoC 停在「回傳一包 JSON」，看不出東西。

所以這一版改成：**先自己寫一段 prompt**，把檢索到的條文與總表對應結果餵進生成式模型，產出一份風險分析報告。它不是 L9 的受控報告，只是規格到位前的出口。

## PoC 目標

三個元件，各自要達成的事。跟前一版最大的差別是 **:tip[Indexer]{content="這套系統裡負責建庫的元件：把法條與總表轉成向量與結構化資料，寫進資料庫"} 不再是獨立的離線 CLI，而是收進 API**：

::::steps
:::step{title="Vector Database"}
鎖定勞基法，結合當前對應的「L1~L3+L6 總表」資料建立 :tip[Embedding]{content="把文字轉成一串數字，語意相近的文字數字也相近，於是「意思像不像」可以用算的"} Database。
:::
:::step{title="API（NestJS）"}
常駐服務，內含四件事——前三件不碰生成式模型，第四件才碰：

1. **Indexer 元件** — 將法條文本與總表資料轉換成向量寫入 Vector Database。以 :tip[NestJS]{content="Node.js 的後端框架，這一版 API 與 Indexer 都跑在上面"} 的 command / 管理端 endpoint 觸發，不再是獨立進程
2. **條文檢索** — 依用戶問句從 Vector Database 撈相關的勞基法條文及解釋，取最相關的內容以 **:tip[Top-K]{content="一次檢索取回最相近的前 K 筆。這一版 K = 5"}** 返回，K 先設為 **5**
3. **總表整合** — 將檢索到的內容與「L1~L3+L6 總表」整合後返回，**此段不需要 :tip[LLM]{content="大型語言模型，也就是會生成文字的那種 AI"} 介入**
4. **風險分析報告** — 把前兩步的結果餵進一段自撰 prompt，交給生成式模型輸出報告。這一段的呼叫全程掛 **:tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"}** :tip[trace]{content="一次請求的完整執行紀錄，事後可以回頭查那一次到底發生什麼"}，記下問句、:tip[token]{content="模型處理文字的最小單位，計費與長度上限都以它計算。中文約一個字一到二個"} 用量、延遲與模型版本
:::
:::step{title="UI"}
**Vite + React（TypeScript）**。一頁就好：輸入白話問句 → 看到撈回來的條文、反查到的 L1~L3 分類、以及最後那份風險分析報告。

UI 是拿來**讓檢索品質可被肉眼檢查**的，談不上產品雛形。純 API 回傳的 JSON 看不出「這五條撈得準不準」，攤在畫面上就看得出來。
:::
::::

:::note{title="Indexer 收進 API 的取捨"}
獨立 CLI 的好處是建庫與查詢完全解耦；收進 API 的好處是**embedding 設定只有一份**：模型名稱、維度、切塊規則不會在兩支程式裡各寫一次然後悄悄長歪。這一版資料量小、只有一個人在跑，選後者。
:::

## 系統邊界

完整系統是**四個模組**：三個有介面，一組是 API。但那組 API 會被信任邊界切成兩半——兩支讀的掛在公開 internet，一支寫的跟法條管理後台關在同一側。PoC 只碰到其中兩格，而且都只做了半格。

| 模組 | 誰在用 | 做什麼 | 暴露面 | PoC 這一版 |
|---|---|---|---|---|
| **客戶前台** | 會員 | 問句進 → 條文、L1~L3 分類、風險分析報告出 | 公開 internet，須登入 | :badge[部分]{variant="warning"} 一頁展示 UI，不做登入 |
| **對外 API · 讀** | API 串接方（會員 key） | 檢索、報告兩支 | 公開 internet，須驗證 ＋ 配額 | :badge[未做]{variant="neutral" outline} PoC 不對外 |
| **法條管理後台** | 顧問師 | 法條與決策樹分類的制定編修，最終 :tip[Embedding]{content="把文字轉成一串數字，語意相近的文字數字也相近，於是「意思像不像」可以用算的"} 進庫 | 不公開，限定 IP | :badge[部分]{variant="warning"} 只有 :tip[Indexer]{content="這套系統裡負責建庫的元件：把法條與總表轉成向量與結構化資料，寫進資料庫"}，編修先用 Excel 頂 |
| **Embedding API · 寫** | 管理端串接方（管理端 key） | 法條與決策樹主題進庫 | 不公開，限定 IP ＋ 管理端 key | :badge[未做]{variant="neutral" outline} 只由 API 內的 Indexer 觸發 |
| **運維管理後台** | 系統管理者 | :tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"} tracing、API metric | 不公開，限定 IP | :badge[部分]{variant="warning"} 只有 Langfuse 自己的介面 |

前台現在是裸的——拿到網址就能問。正式版要補驗證，:tip[JWT]{content="一種帶簽章的登入權杖，伺服器不用查資料庫就能驗證真偽"}／:tip[OAuth]{content="授權框架，讓第三方在不拿到你密碼的情況下代為存取"}／:tip[SSO]{content="單一登入：一組帳號通行多個系統"} 都還在檯面上。但它排在配額前面：**沒有身分，就沒有「這個人這個月用了幾次」**。

寫的那支動的是整個向量庫，跟法條管理後台是同一件事的兩個入口，所以它跟後台待在同一側，**不掛上公開 internet**。網路層擋在門外是第一層；管理端 key 是進了門之後的第二層，兩層都要，別把它併進會員那套驗證。

## 帳號與權限

:::info{title="這一節是推估，等崴仁的表來對"}
交付清單第 2 項的「角色 × 功能 × 資料權限表」**由崴仁提供**，尚未交付。以下是依上一節〈系統邊界〉的使用情境反推的版本，目的是拿去跟他的表對齊、把差異問出來，**不是定案**。
:::

### 四個角色

| 角色 | 身分性質 | 在哪個模組 | 這一版 PoC |
|---|---|---|---|
| **會員** | 人，登入後的使用者 | 客戶前台 | :badge[未做]{variant="neutral" outline} 無登入，拿到網址就能問 |
| **顧問師** | 人，內部 | 法條管理後台 | :badge[部分]{variant="warning"} 編修用 Excel 頂，無帳號概念 |
| **系統管理者** | 人，內部 | 運維管理後台 | :badge[部分]{variant="warning"} 只有 :tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"} 自己的帳號 |
| **API 串接方** | **機器**，代表某個會員 | 對外 API · 讀（會員 key）／:tip[Embedding]{content="把文字轉成一串數字，語意相近的文字數字也相近，於是「意思像不像」可以用算的"} API · 寫（管理端 key） | :badge[未做]{variant="neutral" outline} PoC 不對外 |

**會員**指登入後的使用者。來源可能是自行註冊，也可能由 HRM 訂閱帶進來：**兩者的資料範圍完全相同**，差別只在配額級距，也就是能問幾次。

第四個是這份推估加的。API 的呼叫者是一組 credential：沒有密碼重設、沒有離職停用，卻需要輪替與撤銷。生命週期跟人不同，**別塞進人的角色表裡**。會員 key 與管理端 key 都算在這個角色裡，但兩者不共用驗證，暴露面也不同——管理端 key 只在限定 IP 底下用得到。

:::note{title="為什麼沒有企業帳號這一層"}
會有人問：客戶是企業，為什麼角色表裡沒有企業管理者？

因為這套系統評估的是**外部法律**，不是企業內部的工作規則。使用者拿自己的情境去對勞基法，問句與報告都只屬於問的那個人，沒有**「同事的資料我看不看得到」**這種問題，也就沒有資料存取權限需要按企業切開。

我們有兩個產品：法遵決策系統與 HRM。HRM 才是企業層的東西；法遵決策系統這邊，訂閱 HRM 的會員與自行註冊的會員**權限完全一樣**，訂閱只影響收費標準，而收費標準只影響使用次數。

這是就目前的法遵決策系統而言。日後若要讓企業檢視自己的工作規則，企業層才會需要重新討論。
:::

| 元件 | 選型 |
|---|---|
| **Vector Database** | PostgreSQL + :tip[`pgvector`]{content="PostgreSQL 的向量擴充套件，讓資料庫直接存向量、算相似度"} |
| **API（含 :tip[Indexer]{content="這套系統裡負責建庫的元件：把法條與總表轉成向量與結構化資料，寫進資料庫"}）** | :tip[NestJS]{content="Node.js 的後端框架，這一版 API 與 Indexer 都跑在上面"} + TypeScript + :tip[LangChain]{content="串接模型、資料來源與流程的開發框架"} + Mistral `mistral-embed` |
| **UI** | Vite + React + TypeScript |
| **生成式 :tip[LLM]{content="大型語言模型，也就是會生成文字的那種 AI"}** | **Codex 5.6 Luna**，只用在風險分析報告那一段 |
| **可觀測性** | **:tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"}（:tip[self-host]{content="架在自己的環境裡，資料不出自家雲端"}）**，追蹤報告生成的 AI 足跡與 :tip[token]{content="模型處理文字的最小單位，計費與長度上限都以它計算。中文約一個字一到二個"} 用量 |

Indexer 收進 API 之後要盯的是另一件事：**換 :tip[embedding]{content="把文字轉成一串數字，語意相近的文字數字也相近，於是「意思像不像」可以用算的"} 模型時整庫要重建**。建庫與查詢用不同模型，向量空間對不上，檢索結果會是隨機的，而且**不會報錯**。`labor_articles.embedding_model` 這欄就是為了讓殘留資料被看見。

報告生成這一段用 **Codex 5.6 Luna**。它只掛在最後一段，換掉不影響向量庫，也不影響 L1~L3 的反查結果，是這條路徑上唯一可以晚點再換的元件。

Langfuse 走 **self-host**，跟資料庫一樣放在 GCP。法遵問句帶得動公司名、人名與薪資數字，這種東西不往外送；自架也讓「換模型後回頭比對前後輸出」這件事有地方查。它掛在兩段有模型的地方：入口的 G1 意圖判定與出口的報告生成；embedding 呼叫量大、單價低，記了只會把 :tip[trace]{content="一次請求的完整執行紀錄，事後可以回頭查那一次到底發生什麼"} 洗掉重點，所以不記。

### 技術架構

UI 進、API 出，建庫與查詢都收在同一個 NestJS 服務裡，中間用 PostgreSQL 交棒；報告那一段的呼叫另外側掛 Langfuse。

## PoC 資料結構

兩張表：`labor_articles` 存法條與向量，`decision_tree` 存總表的 85 列決策樹。決策樹的部分參考總表的「L1~L3+L6總表」分頁。

風險分析報告**不進 PostgreSQL**：PoC 階段直接回傳給 UI，不建表。等 L4~L8 規格到位、報告結構定下來再談儲存。

但**歷程不是沒有留**：報告生成的每一次呼叫都寫進 :tip[self-host]{content="架在自己的環境裡，資料不出自家雲端"} 的 :tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"}，問句、輸出、:tip[token]{content="模型處理文字的最小單位，計費與長度上限都以它計算。中文約一個字一到二個"} 用量、延遲與模型版本都在裡面。應用資料庫乾淨，可觀測性平台留痕，兩件事分開看。

```sql title="db/schema.sql" {2,10,44-55}
-- 一次建好，可重跑
CREATE EXTENSION IF NOT EXISTS vector; -- (1)!

CREATE TABLE IF NOT EXISTS labor_articles (
  id              bigserial    PRIMARY KEY,
  law_name        text         NOT NULL DEFAULT '勞動基準法',
  article_code    text         NOT NULL,
  clause_no       text,
  content         text         NOT NULL,
  embedding       vector(1024), -- (2)!
  embedding_model text         NOT NULL DEFAULT 'mistral-embed',
  l1_codes        text[]       NOT NULL DEFAULT '{}',
  l2_codes        text[]       NOT NULL DEFAULT '{}',
  l3_codes        text[]       NOT NULL DEFAULT '{}',
  created_at      timestamptz  NOT NULL DEFAULT now(),
  CONSTRAINT uq_article UNIQUE (law_name, article_code, clause_no) -- (3)!
);

CREATE INDEX IF NOT EXISTS idx_articles_embedding
  ON labor_articles USING hnsw (embedding vector_cosine_ops); -- (4)!

CREATE INDEX IF NOT EXISTS idx_articles_l3
  ON labor_articles USING gin (l3_codes); -- (5)!

CREATE TABLE IF NOT EXISTS decision_tree (
  l3_code              text     PRIMARY KEY,
  l3_origin_code       text     NOT NULL,
  l1_code              char(1)  NOT NULL CHECK (l1_code IN ('A','B','C','D')),
  l1_animal            text     NOT NULL,
  l1_scope             text     NOT NULL,
  l2_code              text     NOT NULL,
  l2_name              text     NOT NULL,
  l3_title             text     NOT NULL,
  enterprise_tone      text     NOT NULL,
  frequency            text     NOT NULL
                                CHECK (frequency IN ('高頻','中頻','低頻')),
  risk                 text     NOT NULL
                                CHECK (risk IN ('高風險','中風險','低風險')),
  initial_mines        smallint NOT NULL CHECK (initial_mines BETWEEN 1 AND 5),
  initial_intervention text     NOT NULL
                                CHECK (initial_intervention IN ('低','中','高','急迫')),
  article_codes        text[]   NOT NULL DEFAULT '{}',

  CONSTRAINT chk_mines_derived CHECK ( -- (6)!
    initial_mines =
      (CASE frequency WHEN '低頻' THEN 1 WHEN '中頻' THEN 2 ELSE 3 END)
    + (CASE risk      WHEN '低風險' THEN 0 WHEN '中風險' THEN 1 ELSE 2 END)
  ),
  CONSTRAINT chk_intervention_derived CHECK ( -- (7)!
    initial_intervention = CASE
      WHEN initial_mines <= 1 THEN '低'
      WHEN initial_mines <= 3 THEN '中'
      WHEN initial_mines  = 4 THEN '高'
      ELSE '急迫' END
  )
);

CREATE INDEX IF NOT EXISTS idx_tree_l2 ON decision_tree (l1_code, l2_code);
```

1. :tip[`pgvector`]{content="PostgreSQL 的向量擴充套件，讓資料庫直接存向量、算相似度"} 的 extension 名稱是 `vector` 不是 `pgvector`，這行放在 :tip[Runbook]{content="逐步操作手冊，照著做就能把環境重建起來"} 的第一步。
2. 允許 `NULL`：Indexer 元件先把條文列載進來，向量再回填，載入與向量化可以分開跑。維度 1024 對應 `mistral-embed`，換模型要一起改，而且整庫都得重跑。
3. 唯一鍵帶 `clause_no`，讓「同一條按項切成多個 chunk」不會互相衝突；重跑 Indexer 時可以 :tip[`ON CONFLICT DO UPDATE`]{content="PostgreSQL 的「有就更新、沒有就新增」，讓建庫可以重跑而不會寫出重複資料"}。
4. :tip[HNSW]{content="一種近似最近鄰索引，犧牲一點精準度，換取大量資料下的查詢速度"} ＋ :tip[cosine]{content="餘弦相似度：比對兩個向量的夾角，1 是完全同向。看方向不看長度"}。資料量只有百來筆，其實全表掃也夠快，但索引先建好，之後擴到函釋與施行細則不用改。
5. GIN 索引給 `l3_codes`，總表整合那一步就是拿檢索回來的條文 `l3_codes` 去比對總表。
6. **初始地雷數是算出來的**，不是另外輸入的一欄：地雷數 = 頻率分（低 1／中 2／高 3）＋ 風險分（低 0／中 1／高 2）。總表 85 列全部吻合、零例外，所以用 `CHECK` 守住，之後顧問師改了風險等級卻忘了改地雷數，載入當下就會被擋下來。
7. 介入程度同理，就是說明書 L8 的門檻：1 顆低、2–3 顆中、4 顆高、5 顆以上急迫。85 列同樣零例外。

## AI 介入

整條流程只有三個地方允許模型介入：入口的 **G1 意圖判定**、出口的 **L9 報告**與 **L10 顧問推薦**。中間那段全部走規則引擎：L1–L3 分類是反查、L6 條文對照，以及使用者輸入的守門。L4–L8 這一版整段不做。這條界線要寫進規格，不然實作時很容易被一句「這裡順便叫模型判斷一下」慢慢侵蝕掉。

執行這條界線的是 :tip[G0~G3]{content="四道閘門：規則守門、意圖判定、檢索幾何、輸出白名單"} 四道閘門。它們的判定方式、門檻與擋不住的東西留到〈安全與稽核〉講，這一節只標出十四個節點裡哪三個碰得到模型。

### 介入點與硬限制

| 層次 | 這一版怎麼做 | 方式 | 硬限制 |
|---|---|---|---|
| 使用者輸入 | 長度／次數／檔案限制 | :badge[規則]{variant="neutral" outline} | 拒絕濫用與超量上傳；不判斷內容 |
| **G1 意圖判定**（L1 分流前） | 判 `in_scope` 與 `has_directive`，:tip[溫度 0]{content="控制隨機性的參數。0 代表同樣的輸入盡量給同樣的輸出，適合用來做判定"}、獨立呼叫 | :badge[AI]{variant="warning"} | 逾時或格式錯誤一律拒絕（:tip[fail closed]{content="出錯時倒向拒絕而不是放行。寧可擋錯，不可放錯"}）；不與報告生成共用 :tip[context]{content="模型這一次呼叫看得到的所有文字。沒放進去的東西，它就洩不出來"} |
| L1–L3 分類 | 由檢索到的 L6 條文回推總表 | :badge[反查]{variant="success"} | 零 AI；無命中走 :tip[`unclassified`]{content="系統的「無法分類／超出範圍」出口。誠實說不知道，不硬湊答案"} 出口，不強制歸類 |
| L4–L8 | 不做（規格未到） | :badge[規則]{variant="neutral" outline} | — |
| L6 條文對照 | 向量檢索 :tip[Top-K]{content="一次檢索取回最相近的前 K 筆。這一版 K = 5"} = 5 ＋ 條文代碼 join | :badge[規則]{variant="neutral" outline} | 未經顧問核准，AI 不得自行擴寫法律結論 |
| L9 報告 | 自撰 prompt 產出風險分析報告 | :badge[AI]{variant="warning"} | 固定章節與欄位；不得新增事實、條文或法律結論 |
| L10 顧問推薦 | 不做（規格未到） | :badge[AI]{variant="warning"} | — |

`decision_tree` 裡有四個欄位**由規則產生，模型碰不到**：`frequency`／`risk` 是 L3 題型的預設頻率與風險，由顧問師人工設定；`initial_mines`／`initial_intervention` 是 L7 地雷數與 L8 介入程度的**初始值**，由前兩欄用公式算出、有 :tip[`CHECK`]{content="資料庫層的規則，不合法的值直接寫不進去，不靠程式自律"} 守著（實際值要等 L5 追問加減地雷後才算得出來，這一版不做）。模型只能讀它們寫進報告，不能自己生一個地雷數或介入程度出來。

### 權限限縮

擋 B 的主力是砍掉模型的權限面，禁止語句只是輔助：

- **不能決定範圍**：範圍由檢索幾何與規則決定
- **不能引用未經檢索的條文**：條文原文只從 DB 取，輸出的條文代碼必須落在本次檢索結果內
- **不能有副作用**：沒有工具呼叫、沒有寫入權、沒有外部存取
- **:tip[system prompt]{content="給模型的固定角色與規則，使用者看不到，也改不到"} 假設終將公開來設計**：不放金鑰、不放商業邏輯

結果是模型的 :tip[context]{content="模型這一次呼叫看得到的所有文字。沒放進去的東西，它就洩不出來"} 只剩公開法條 ＋ 使用者自己的輸入 ＋ 報告範本，C 類威脅無物可洩。

### 稽核紀錄

規則版本、Prompt 版本、模型版本與輸入輸出掛在 :tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"} 的 trace metadata 上，不另外建表。閘門決策一併記：哪一關擋下、`top1`／`mean@5`／`margin`、G0 命中的規則、G1 的 `in_scope`／`has_directive` 判定。同一使用者短時間多次命中 → 升級處置（限流／暫停／人工檢視）。

**稽核只能事後發現，不能防禦**，尤其是工具呼叫那類側門，查得出來時資料已經走了。

PoC 階段會記**完整會員問句**，問句裡可能帶公司名、人名與薪資數字。這是已知且被接受的取捨：:tip[去識別化]{content="把公司名、人名、金額這類可辨識的資訊移除或代換掉"}要做，但**不在 PoC 範圍**。:tip[self-host]{content="架在自己的環境裡，資料不出自家雲端"} 是這個取捨成立的前提：資料不出 GCP。

代價要說清楚：全站問句都進 Langfuse，而 Langfuse 只有系統管理者進得去，於是**跨會員原始問句只有他讀得到**，連顧問師都沒有這條路（見〈帳號與權限〉的資料權限表）。他改不動任何東西，卻讀得到所有人的東西：這裡的「唯讀」是全站最寬的讀取權，不是最小的。

記是一定要記。剩下的是記了之後怎麼管：

1. Langfuse 的問句欄位去識別化（如上，不在 PoC 範圍）
2. 運維後台與 Langfuse 拆成兩組帳號，metric 給系統管理者、trace 另設審核流程
3. 查看 trace **這件事本身**也要留紀錄

建議 **3 打底、2 為目標**：去識別化排不進 PoC，但「查看者也被記錄」成本近乎為零，現在就能做。

*使用者確認與顧問轉介的紀錄欄位待補。*

模型會逾時、會回傳不合 schema 的東西。這是常態。每一種失敗都要有預先決定好的退路：

| 失敗情境 | 降級行為 | 使用者看到 |
|---|---|---|
| 分類模型逾時或格式不合 schema | 退回純反查結果 | 條文與分類照常顯示，標示「未經語意分類」 |

這一套不問答得對不對，只問有沒有守規矩。作法是**餵假的模型輸出給 G3 驗證器，繞過模型**：等真實模型自然產生違規太慢，而且不可重現。G3 是純程式，就該用單元測試測。

## Token 與成本

數字從 :tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"} 來：單次報告的 :tip[token]{content="模型處理文字的最小單位，計費與長度上限都以它計算。中文約一個字一到二個"} 用量、延遲與失敗率都在 :tip[trace]{content="一次請求的完整執行紀錄，事後可以回頭查那一次到底發生什麼"} 裡，不必另外埋計數器。:tip[embedding]{content="把文字轉成一串數字，語意相近的文字數字也相近，於是「意思像不像」可以用算的"} 那段不記，所以這一節談的成本只涵蓋報告生成。

## PoC 任務拆解

::::steps
:::step{title="Vector Database" status="current"}
- 在 **GCP** 建立 PostgreSQL + :tip[`pgvector`]{content="PostgreSQL 的向量擴充套件，讓資料庫直接存向量、算相似度"} 環境
- 撰寫 PostgreSQL + `pgvector` 環境建置的 **:tip[Runbook]{content="逐步操作手冊，照著做就能把環境重建起來"}**

Runbook 別留到最後補。它的價值在逼你把手動做過的每一步寫下來，沒寫下來的那幾步，就是之後重建環境時卡住的地方。
:::
:::step{title="API 1｜Indexer 元件"}
- 在 :tip[NestJS]{content="Node.js 的後端框架，這一版 API 與 Indexer 都跑在上面"} API 內實作 **:tip[Indexer]{content="這套系統裡負責建庫的元件：把法條與總表轉成向量與結構化資料，寫進資料庫"} 元件**，將勞基法條文與「L1~L3+L6 總表」資料轉換成向量／結構化資料，存入 Vector Database
- 以管理端 command／endpoint 觸發，可重跑（:tip[`ON CONFLICT DO UPDATE`]{content="PostgreSQL 的「有就更新、沒有就新增」，讓建庫可以重跑而不會寫出重複資料"}）
:::
:::step{title="API 2｜條文檢索"}
- 根據用戶問題，從 Vector Database 檢索相近的勞基法條文及解釋，:tip[Top-K]{content="一次檢索取回最相近的前 K 筆。這一版 K = 5"} = 5，回傳給用戶
:::
:::step{title="API 3｜總表整合"}
- 將檢索到的勞基法條文及解釋與「L1~L3+L6 總表」整合，找到匹配的資料後回傳給用戶
:::
:::step{title="API 4｜風險分析報告"}
- 撰寫 prompt，把前兩步的條文與 L1~L3 對應結果餵入生成式模型，輸出風險分析報告
- **這一步是暫代**：L4~L8 規格交付後，這段 prompt 要整個換掉，不要在上面疊功能
:::
:::step{title="API 5｜可觀測性接線"}
- 在 **GCP** 架設 :tip[self-host]{content="架在自己的環境裡，資料不出自家雲端"} **:tip[Langfuse]{content="開源的 LLM 可觀測性平台，記錄每一次模型呼叫的輸入、輸出、token 與延遲"}**（含自己的 PostgreSQL），撰寫建置 Runbook
- 報告生成的呼叫掛上 :tip[trace]{content="一次請求的完整執行紀錄，事後可以回頭查那一次到底發生什麼"}：記問句、輸出、:tip[token]{content="模型處理文字的最小單位，計費與長度上限都以它計算。中文約一個字一到二個"} 用量、延遲、模型版本與 Prompt 版本
- 降級事件一併上報，標上降級原因
:::
:::step{title="UI"}
- 以 **Vite + React（TypeScript）** 做一頁展示介面：輸入問句 → 條文清單 → L1~L3 分類 → 風險分析報告
- 目的是讓檢索品質可被肉眼檢查，不做登入、不做多頁
:::
