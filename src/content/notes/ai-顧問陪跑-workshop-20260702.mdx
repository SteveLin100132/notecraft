## **會議主軸**

這次討論主要分成兩大段:前半段是 AI-assisted 開發流程、agent 分工、PR/Issue/版本控管與部署流程的調整;後半段是「AI 輔助勞動法遵決策支援系統」的產品定位、資料結構、顧問協作與技術可行性。

:::tip{title="整體判斷"}
目前真正的瓶頸不是技術實作,而是**「規則資料與顧問知識如何被結構化」**。如果前面的分類、決策樹、風險評分與條文對應做錯,後面的 AI 回答、檢測報告、顧問推薦都會一起錯。
:::

## **一、開發流程與 AI Agent 工作流調整**

目前團隊已經開始把 AI-assisted development 流程拆成不同角色,例如 SA、SD、DBA、QA 等 sub-agent,但實際運作中發現幾個問題。

:::note{title="1. Agent 分工的資訊斷層" collapsible}
角色拆分後,部分 agent 只專注自己的任務,導致 UI、UX、API 串接、prototype 參照等資訊沒有完整傳遞。例如 SA 有讀 prototype,但到 SD 或後續 task 產生時,前端畫面與 design token 沒有被正確納入,導致 AI 產出的畫面沒有照既有 prototype 與 design system 走。
:::

:::note{title="2. 流程文件補強" collapsible}
團隊正在補強流程文件,要求 proposal、task、design 產出時要同時參考 prototype、UI design、design token 與 API 文件,避免 AI 自己亂設計畫面或漏掉前端任務。
:::

:::note{title="3. DB schema 與 migration 同步" collapsible}
DBA agent 被要求在做 migration 時回寫 `schema.md`,但實際上偶爾會漏掉。討論後認為,只寫在規則裡不夠,最好把這類必要步驟拆成 **task skeleton**,讓 agent 執行時有明確待辦,並讓 QA 後續檢查是否完成。
:::

:::note{title="4. PR tag、issue template、release note 收斂" collapsible}
現在 tag 太多,容易無限增長,建議不要把 feature、sprint、需求、模組全部塞進 label,而是改用 **milestone、module 或 issue 本身**管理。release note 則不建議寫得像 changelog 一樣過細,一個 PR 或 issue 一行即可。
:::

:::note{title="5. Codex / PR review 觸發方式調整" collapsible}
現在若每次 push 都觸發 review,容易出現一直 review、一直修、沒完沒了的狀況。建議:

- 關掉自動每次觸發,改成**手動呼叫 review**
- 在 review guide 裡要求它一次掃完問題,列出 :badge[P0]{variant="danger" size="sm"} :badge[P1]{variant="warning" size="sm"} :badge[P2]{variant="info" size="sm"} 清單,優先處理真正重要的問題
:::

:::note{title="6. 版本號管理" collapsible}
建議以 **npm version** 類似流程為主,避免在 GitHub secret 裡手動維護版號。`patch` / `minor` / `major` 的判斷仍由人決定,工具只負責一致更新版本。
:::

:::note{title="7. 開發環境實務問題" collapsible}
包括 `npm install` / `npm ci` 的安全性、package lock 的版本鎖定、migration 是否在 server start 時自動跑、local port 衝突、殭屍行程、Docker 化部署到 GCP 等。

整體方向:**盡量鎖版本、減少自動拉最新套件**,並考慮用 Docker 降低環境差異與 port 衝突。
:::

## **二、產品定位：不是法律問答機，而是法遵風險檢測器**

後半段重點在「AI 輔助勞動法遵決策支援系統」。

:::tip{title="產品定位定調"}
**不是**直接回答法律問題的 AI 律師,**也不是**取代顧問,而是一個**前置檢測系統**。

它比較像**健康檢查或醫療檢測流程**:使用者一開始以為只是小問題,但系統透過分類、追問與風險評估,協助找出背後可能涉及的法遵風險,最後再導向真人顧問。
:::

這個定位很重要,因為如果產品被設計成「使用者問什麼,AI 就直接回答什麼」,風險會很高。勞動法問題通常需要事實釐清,例如員工身分、工時制度、給付方式、請假類型、公司制度等。AI 如果沒有先問清楚,很容易頭痛醫頭、腳痛醫腳,給出錯誤或過度簡化的建議。

因此,目前更合理的產品敘事是:

> 企業或 HR 輸入一個問題後,系統先判斷這個問題可能屬於哪一類勞動法風險,再透過決策樹追問必要事實。使用者回答後,系統計算風險分數、指出可能踩到的地雷、對應相關條文,並產出一份可控範圍內的白話檢測報告。若風險高或問題複雜,系統再推薦真人顧問介入。

## **三、決策樹與資料結構設計**

目前構想是把勞基法相關問題拆成多層分類,大約是 :badge[L1]{variant="info" size="sm" outline} 到 :badge[L10]{variant="info" size="sm" outline} 的流程。

- **L1–L3**:法律問題分類,例如先分成幾個大類,再往下細分子類與細項。會用「動物」作為可愛化的分類意象(獵犬、蜜蜂、大象、貓頭鷹等),但實際背後是勞動法主題分類。
- **L3 / L4 之後**:每個分類會有對應的必要事實與追問問題。每個問題可能是單選,使用者不同選項會對應不同風險分數或「地雷」數。最後系統會依據回答結果計算風險程度,並對應到相關條文與顧問介入程度。

**這套系統的核心資料包括:**

1. 勞基法條文與其分類
2. 每個分類下的必要事實
3. 每個必要事實對應的追問問題
4. 每個選項對應的風險分數
5. 每個分類與條文的對應關係
6. 每個顧問擅長處理的領域
7. 最後檢測報告的產出規則

:::warning{title="資料正確性不是工程能單獨解決的"}
資料結構設計會是技術端的重點,但**分類是否正確、條文是否放對、風險高中低是否合理、追問問題是否完整**,都需要法律 / 人資顧問逐條驗證。
:::

## **四、顧問協作與資料驗證**

顧問端會被要求參與資料校正。初步會請多位顧問檢查分類、條文對應、風險頻率、風險嚴重度與追問邏輯。

:::info{title="多顧問分歧的處理方式"}
不同顧問可能會對同一個項目給出不同判斷,例如有人認為風險高,有人認為風險中或低。討論中提到可以類似**作文閱卷**的方式處理:

- 差異不大 → 直接接受
- 差異很大 → 標記出來讓副總或更資深的人做最後判斷
:::

也討論到,顧問不一定會完整填寫,可能有人會偷懶、用 AI 幫忙填、或只填一部分。因此建議用 Google 表單或網頁介面收集資料,至少可以看到填寫時間、操作痕跡,降低亂填的風險。

:::tip{title="工程端只接最終版本"}
最後不需要知道五個顧問各自怎麼評,只需要拿到整理後的**最終資料表**。顧問討論與分歧處理應該在**業務 / 專業端先收斂**,工程端只接最終版本。
:::

## **五、AI 的角色與護欄**

AI 在這個系統裡有兩個主要介入點:

:::::tabs
::::tab{label="前段分類"}
使用者輸入問題後,AI 要協助判斷這個問題屬於哪一類風險。這裡有兩種做法:

1. 讓 AI 先檢索**所有條文與分類**,再判斷使用者問題可能落在哪裡
2. 先粗分類,再**一層一層載入相關資料**往下判斷

:::success{title="傾向做法 2:分層載入"}
一次塞入太多條文與資料,AI 容易分心或關聯錯誤。勞基法本身條文數量不算巨大,但如果再加上函釋、解釋令與案例,資料量會變得複雜,必須實驗 :tip[embedding]{content="把文字轉成向量,用相似度做語意檢索"}、:tip[top-k retrieval]{content="檢索與查詢語意最相近的前 K 筆資料"}、分層載入等方式。
:::
::::

::::tab{label="後段報告產生"}
系統依照前面決策樹與風險計算結果,讓 AI 產出一份**白話但受控**的檢測報告。這份報告**不是自由發揮**,而是根據已收集到的事實、分類、風險分數、條文對應與顧問推薦邏輯生成。

:::warning{title="護欄設計是重點"}
系統不應該讓 AI 直接回答超出範圍的法律問題。如果使用者問得太模糊或找不到明確分類,應該讓使用者確認:「你是不是要問這一類問題?」或讓他從候選分類中選擇。

**整體策略:寧願多防呆,也不要讓 AI 自信亂答。**
:::
::::

## **六、商業模式與產品價值**

:::success{title="核心價值主張"}
這套系統的商業價值**不是單次問答**,而是把顧問服務**從被動接案變成主動風險管理**。
:::

目前顧問案常見狀況是:企業遇到問題才找顧問,顧問解決完後案子結束,後續是否又走歪很難追蹤。這個系統可以變成類似**定期健檢或會員制服務**,讓企業每半年或定期檢測一次,持續追蹤法遵風險。

也就是說:

- **前端**:用較低門檻導入一個風險檢測工具,讓企業發現自己原本沒意識到的問題
- **後端**:由顧問根據檢測結果主動介入,提供更高價值的服務

這點對商業化很重要,因為它不是單純賣 AI 工具,而是把 AI 變成**顧問業務開發、風險揭露、定期追蹤與顧問推薦的入口**。

## **七、擴充方向**

:::warning{title="第一階段只聚焦勞基法"}
不建議一開始就把**性平法、就服法、海外法規**等全部塞進來。原因是資料結構、分類規則、風險評分與顧問驗證流程都還需要先跑順。
:::

未來若勞基法流程穩定,可以把同一套 L1 到 L10 架構擴充到其他法規。海外版本也有可能,例如越南勞動法,但那時候本地顧問未必懂海外法,就需要交給**當地法律事務所或專家**校正資料。

:::tip{title="真正要產品化的是流程,不是法條"}
關鍵不是把 AI 丟去讀海外法條,而是把「**法規資料結構化、顧問校正、決策樹驗證、報告生成**」這套流程產品化。若流程本身可複製,海外法規才有擴充可能。
:::

## **八、主要風險與下一步**

### 三大風險

:::danger{title="1. 資料前處理錯誤"}
分類、條文、必要事實、風險分數只要前面錯,後面 AI 再強也只是**把錯誤包裝得更漂亮**。
:::

:::danger{title="2. 顧問校正成本被低估"}
現在看起來似乎只是填黃色欄位或改分類,但實際上越往下層,項目數會快速膨脹,**可能從幾十個變成上千個判斷點**。
:::

:::danger{title="3. AI 分類準確率未知"}
到底要用全文條文、embedding、分層分類、top-k retrieval,還是混合方式,目前都需要實驗。**不能先假設模型一定能穩定判斷。**
:::

### 下一步

::::steps
:::step{title="完成 L1–L3 分類與顧問驗證" status="current"}
先完成勞基法 L1 到 L3 分類與顧問驗證。
:::
:::step{title="建立最終資料表"}
建立一份可被工程端使用的最終資料表,包含**分類、必要事實、追問、選項、風險分數、條文對應**。
:::
:::step{title="小型分類實驗"}
測試使用者自然語言問題能否穩定分類到正確 L3,並比較「**全文檢索**」與「**分層分類**」哪個效果更好。
:::
::::

:::info{title="結語:守住產品差異"}
這個產品方向是成立的,但成立點**不是**「AI 會回答勞基法問題」,而是:

> 把顧問的前置診斷流程結構化,讓 AI 負責收斂問題、揭露風險、生成初步報告,再把真正高風險問題導給顧問。

這個差異要守住,否則產品會掉回**高風險、低可信度的法律問答機**。
:::
