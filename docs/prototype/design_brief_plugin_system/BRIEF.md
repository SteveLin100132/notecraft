# 設計簡報 — NoteCraft Plugin System

完整規格見 [docs/notecraft-plugin-system.md](../../notecraft-plugin-system.md)（v0.2.0，已定案）。
這份只挑**設計會用到**的部分，不必讀完規格。

---

## 1. 一句話

讓專案裡的結構化 JSON 資料檔，被一個「可安裝的渲染器」畫成網站上的一個頁面。

## 2. 三個角色，一條線

```
作者寫一份 JSON          docs/planning/schema.json
    ↓
作者寫一條映射            .notecraft/plugins.json
                         { "plugin": "er-diagram-renderer",
                           "files": ["planning/schema.json"] }
    ↓
build 時多出一頁          /view/planning/schema
```

渲染器（plugin）是從 GitHub 裝下來的，一個 plugin 就是幾個檔：`renderer.tsx`（畫面）、
`notecraft-plugin.json`（身分證）、`schema.json`（資料驗證規格）。

## 3. 這與筆記的差別（設計上最關鍵的一點）

| | 筆記 | 資料檔 |
| :-- | :-- | :-- |
| 原始檔 | `.md` / `.mdx` | `.json` |
| 內容從哪來 | 人寫的文章 | 結構化資料，由渲染器畫成圖 |
| 版心 | 760px，為閱讀長文設計 | **需要全寬**，ER 圖是五欄橫向佈局 |
| 頁面獨有資訊 | 標籤、系列、閱讀進度 | 原始檔路徑、渲染它的 plugin |

**設計上要回答的核心問題**：讓使用者在一秒內知道「這頁不是我寫的文章，是一份資料被畫出來的」，
但又不要讓它看起來像是另一個 app。

## 4. 要設計的畫面

### 4.1 `/view/<path>` 資料檔檢視頁（A 輪，主畫面）

| 區塊 | 必須有 | 備註 |
| :-- | :-- | :-- |
| 頁首 | 標題、描述、原始檔路徑、更新時間、plugin id | 標題與描述來自 JSON 的 `meta` 區塊；沒寫就退回用檔名 |
| 內容 | plugin 渲染出來的東西（用 ER 圖截圖當佔位） | **要能全寬**，這是這頁存在的理由 |
| dev 工具列 | 「以 VS Code 編輯」按鈕 | 只在本機開發時出現，正式環境完全隱藏 |

**不包外框卡片**。既有的 `GeneratedFrame`（虛線外框 + 放大檢視按鈕）在這頁是多餘的 ——
這頁本身就是全寬，再套一層放大檢視是重複功能。

### 4.2 側邊欄新增一區（B 輪）

既有五項：總覽 Dashboard / 筆記 Notes / 系列 Series / 標籤 Tags / 關於 About。
第六項指向資料檔清單。

**需要你提案**：
- 這一項叫什麼？中英各一（既有都是雙語形式）。候選方向：資料 Data、檢視 Views、外掛 Plugins。
  「Plugins」偏向講機制而非內容，「資料」偏向講內容 —— 使用者點進去看到的是內容，不是外掛管理。
- 用哪個 lucide icon（既有用 dashboard / notes / layers / tag / about 這組概念）

### 4.3 資料檔清單頁（B 輪）

側邊欄新項目點進去的頁。每筆要有標題、描述、原始檔路徑、渲染它的 plugin、更新時間。

**需要你提案**：要不要能依 plugin 篩選。一個專案可能同時裝三四個 plugin，
但也可能只裝一個 —— 只有一個 plugin 時篩選器要不要消失？

### 4.4 `/notes` 列表裡的資料檔卡片（B 輪）

已定案：資料檔也會出現在筆記列表，與筆記混排（列表與格狀兩種檢視都有）。
既有筆記卡片的完整結構見 `context-ui.md` §3。

**需要你提案**：怎麼讓它在並排時一眼可辨，但不破壞列表的節奏。
可動的地方：左上角那個 42×42 的 icon 方塊（筆記是藍底 `FileText`）、右上角的徽章列、
底部標籤列（資料檔沒有標籤，那一列要放什麼或留白）。

⚠️ 排序時間用檔案的 mtime —— 筆記有 frontmatter 的 `updatedAt`，資料檔沒有。
兩者混排時「3 天前」這個標示的語意會略有不同，設計上不必特別處理，知道即可。

### 4.5 MDX 內嵌（B 輪）

同一份資料也能嵌在筆記內文裡，此時**要**包既有的 `GeneratedFrame` 外框卡片
（見 `note-detail.png`）。

**需要你提案**：既有外框是為「AI 生成的元件」設計的，上面有 `@ai-visualize` 的標示與
「在 Claude Code 中重新生成」按鈕。資料檔來源不同（不是 AI 生成、重新生成沒有意義），
外框上的標示要不要跟著不同？

### 4.6 錯誤狀態（B 輪）

渲染器在瀏覽器裡出錯 → 該區塊顯示錯誤卡片，頁面其他部分照常。
要有：出錯的 plugin id、資料檔路徑、以及「不是你的筆記壞了」的安心感。

**不需要設計的錯誤**：plugin 沒裝、JSON 壞掉、資料不合 schema —— 這些一律 build 失敗，
訊息出現在終端機，不是網頁。

### 4.7 系列整合（C 輪）

NoteCraft 既有「系列」：把數篇筆記串成有順序的閱讀路徑。相關畫面有三處 ——
系列總覽頁 `/series`、系列詳情頁 `/series/[id]`（整體進度 + 逐章清單）、
以及筆記頁底部的系列導覽（章節清單 + 上一篇/下一篇卡片）。

**新規則：資料檔頁也可以是系列裡的一章，與筆記一視同仁。**

閱讀進度的機制值得先講清楚，因為它決定了這件事為什麼成立：進度**不是**靠捲動比例算的，
而是「開啟該頁 → 自動轉為閱讀中」「使用者手動按 → 已完成」，三態存在瀏覽器。
所以資料檔頁參與進度沒有任何技術或語意上的障礙。

| 畫面 | 要處理什麼 |
| :-- | :-- |
| 系列詳情頁的章節列 | 既有每列有：序號、狀態點、標題、描述、`@ai-visualize` 標記數徽章。資料檔沒有標記數，連結指向 `/view/` 而非 `/notes/` |
| 筆記頁底部的系列導覽 | 章節清單混入資料檔項目；「下一篇」剛好是資料檔時的卡片 |
| 資料檔頁自己的系列導覽 | `/view/<path>` 也要有同一組導覽。注意：導覽維持一般版心，**不要**跟著 A 輪的全寬內容一起撐開 |
| 進度的三個顯示位置 | 系列卡進度條、詳情頁整體進度、章節列狀態點。數字呈現完全不變 |

**需要你提案**：資料檔那一列怎麼被認出來，同時**不看起來像次等的附件**。
它是正式的一章、計入分母、可被標記完成 —— 視覺上要是「不同種類」而不是「比較不重要」。
這個分寸是這一輪的核心。

**不要動**：系列總覽頁的系列卡封面（漸層 + icon 徽章 + 篇數 chip），那塊不受影響。

## 5. 硬約束

| 項目 | 規則 |
| :-- | :-- |
| 色彩 / 字級 / 間距 / 圓角 / 陰影 | **只用既有 token**（`context-ui.md` §4 有完整清單），不新增任何值 |
| icon | 一律 lucide-react，**禁用 emoji** |
| 文案 | 繁體中文；技術名詞（plugin id、檔案路徑、副檔名）保持原文 |
| RWD | 不做斷點設計，桌機 1440 一種寬度 |
| 動畫 | 200–400ms ease-out，需尊重 `prefers-reduced-motion` |
| 不要動 | 既有側邊欄五項、筆記頁版型、ER 圖本身的視覺 |

## 6. 一句話總結你要交的東西

（側邊欄項目怎麼命名、資料檔卡片怎麼區分、內嵌外框要不要改標示、
